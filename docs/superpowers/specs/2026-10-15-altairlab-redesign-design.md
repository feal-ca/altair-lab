# AltairLab redesign

Date: 2026-10-15
Status: draft, awaiting review

## Purpose

AltairLab is a browser app for practising Python Altair. You get a target chart, write Altair code that runs in the browser through Pyodide, and a checker tells you what still differs from the target. It's shared with classmates from a data-visualisation course and should also make sense to anyone who arrives without that context. The interface is in English.

The current version is a single 1,650-line `App.jsx` generated by another model. The idea works, but the code has real bugs (listed below), the checker is unreliable, and the UI crams everything into one screen with a generic dark slate and indigo look. This redesign keeps every existing feature, adds a sandbox, restructures the screens and gives the app its own visual identity.

## Decisions taken with the user

| Topic | Decision |
|---|---|
| Audience | Classmates plus the general public; must work without course context |
| Language | English UI |
| Features kept | Curated exercises with hints, exercise generator, CSV upload |
| Feature added | Free sandbox (editor + dataset, no grading) |
| Teaching content | Practice only; each exercise carries a short concept note and a docs link |
| Checker | Compare the Vega-Lite spec part by part, kept simple |
| Progress | Saved in `localStorage` |
| Layout | Three panes: narrow exercise rail, brief + editor, output |
| Visual style | "Lab notebook", Graphite palette: neutral grey paper with grid, graphite ink, vermilion accent, Fraunces headings, Instrument Sans UI, JetBrains Mono code |
| Hosting | Public repo `feal-ca/altair-lab`, GitHub Pages at `https://feal-ca.github.io/altair-lab/` |

## Bugs in the current code that this fixes

- `deploy.yml` uses `cache: 'npm'` with no lockfile, so `setup-node` fails before building.
- Exercise 10's target uses `INITIAL_DATASETS.eu_lollipop.rows`, which holds 5 of the 10 countries.
- Generated exercises build their target from `dataset.rows`, which for several datasets is a truncated preview (tennis 5 of 35 rows, Priestley 4 of 24, smoking 5 of 10).
- Autocomplete and column cards append text at the end of the file instead of at the cursor, and don't replace the typed prefix.
- Tab moves focus out of the editor.
- Pyodide loads twice in development (StrictMode double effect, no guard).
- User code runs on the main thread, so an infinite loop freezes the tab.
- The runner can leave a stale chart on screen and, when no chart exists, can call `alt.to_json()` on the module.
- The checker compares only the first layer's encodings, counts transforms instead of comparing them, and ignores types, titles, scales and mark properties.
- Tailwind is loaded through its development CDN script; Vega packages use unpinned major versions.
- Nothing persists across reloads.

## Screens

### Top bar

`AltairLab` wordmark, two sections (Exercises and Sandbox) and the Python status. While loading, the status shows the current step ("loading pandas", "installing altair"). On failure it shows the error and a Retry button.

### Exercises (`#/ex/<id>`, default route)

#### Rail

About 170 px wide, collapsible to zero, and a drawer below 900 px. Exercises are grouped by topic:

- Basics: 1 to 4
- Transforms & scales: 5 to 7
- Layering: 8 to 12 and 14
- Advanced: 13, 15, 16
- Generated (when any exist)

Solved exercises show a check. The footer holds a "+ New exercise" button.

#### Brief

Number, level and concept on one line, then the title and the task text. Below it sit three expanders:

- *Hints*: revealed one at a time. After the last one, "Show solution", then "Load into editor", which asks for confirmation before overwriting the user's code.
- *Data*: one card per column with name, type letter and range or sample values. Clicking a card inserts `'column:T'` at the cursor. Under the cards, a `head(5)` table.
- *Concept*: one to three sentences on the idea the exercise practises, plus a link to the matching page of the Altair docs.

#### Editor

CodeMirror 6 with Python highlighting, Tab to indent, and completion for the Altair API and the current dataset's column names. Code runs 600 ms after typing stops and on Ctrl/Cmd+Enter. A Reset button restores the starter code. The starter code always includes the dataset setup (imports and the DataFrame or URL); the "imports only / blank" toggle is removed.

#### Output

*Target* sits above *Yours*. Python errors replace the chart inside *Yours*, showing the message and the user's line number. Below the charts, the check list ("4 of 6 checks"). When every check passes, the exercise is marked solved, a "Solved" mark appears and a "Next →" button takes you on.

### Sandbox (`#/sandbox/<datasetId>`)

The rail lists datasets instead of exercises: built-in ones, the user's CSVs and a "+ Add CSV" entry. The rest is the editor, a single output panel and the Data expander. No checking. Code is saved per dataset.

### New exercise dialog

Pick a dataset (built-in, one of the user's CSVs, or upload a new CSV right there) and a level. The generated exercise is added to the Generated group, saved, and opened.

### Small screens

Below 900 px the rail becomes a drawer and the panes stack: brief and editor first, output after.

## Visual system

Tokens taken from the approved mockup (Graphite):

- Paper `#f4f4f2` with an 18 px grid in `#e3e3df`; sheets (editor, chart cards) `#fcfcfb`
- Ink `#1c1c1c`, secondary ink `#444`, muted `#767676`, faint `#adadaa`, rules `#cacac4`
- Accent vermilion `#e0452b`, success `#2f7a55`
- Code: keywords `#3a5f8a`, strings `#8a5a1a`, numbers in the accent, comments faint italic
- Fraunces for headings and group labels (italic for labels), Instrument Sans for UI text, JetBrains Mono for code, numbers and metadata
- The active rail item is inverted (ink background, paper text); checks are marked with an accent tick
- Chart cards carry a thin border and a 2 px offset shadow, with no rounded corners beyond 2 px

Fonts are bundled with `@fontsource` packages, so nothing is fetched from Google at runtime. Every chart (target, yours, sandbox) is embedded with the same base Vega config for font and axis, grid and title colours, so target and yours always look alike. A spec's own `config` takes precedence over the base, and mark colours are never touched.

## Architecture

### Stack

- Vite and React 19, plain CSS with custom properties. Tailwind is removed.
- `vega`, `vega-lite` 6 and `vega-embed` 7 from npm, pinned in the lockfile.
- Pyodide 314.0.7 (Python 3.14) loaded from jsDelivr inside a module Web Worker. Packages: `pandas` from the Pyodide distribution, `altair==6.3.0` and `vega_datasets` through `micropip`.

Altair 5.5.0 does not import on Python 3.14 (`TypedDict(closed=True)` raises `TypeError`). All 16 curated solutions were run unchanged under Altair 6.3.0 on Pyodide 314.0.7 and produced valid specs, so the app moves to Altair 6.3 and Vega-Lite 6.

### Python worker

`lib/python/worker.js` loads Pyodide and the packages, reporting each step to the main thread. It defines a runner that:

1. Parses the code with `ast`, executes everything except the last statement, and evaluates the last statement if it is an expression.
2. Uses that value if it is an Altair chart (`isinstance(v, alt.TopLevelMixin)`); otherwise uses the last variable bound to an Altair chart.
3. Returns the spec as JSON, or a structured error: message, exception type and the line number in the user's code. If no chart is found it returns a specific "no chart" result telling the user the last line should be a chart expression.

`lib/python/client.js` wraps the worker in a promise API (`run(code) → {spec} | {error} | {noChart}`) and tags each run with an id so stale results are dropped. If a run takes longer than 10 seconds the client terminates the worker, starts a new one and reports "Your code ran too long, so Python was restarted."

`vega_datasets` loaders that download data (`data.cars()`) can't work in Pyodide because there are no sockets. The curated exercises use `.url` or bundled local datasets (`data.barley()`), which do work; the error for a failed download explains the `.url` form.

### Content and targets

- `content/datasets.js`: each dataset has its setup code, column metadata and either full inline rows or a URL plus a five-row preview. The `head(5)` table reads only the preview field.
- `content/exercises.js`: the 16 curated exercises with id, title, level, topic, task text, hints, concept note, docs link and solution code. Hand-written `targetSpec` JSON is removed.
- `content/targets.json`: generated by `scripts/build-targets.mjs`, which runs every solution in Pyodide under Node and writes the resulting specs. It fails if any solution errors. Committed to the repo so targets render instantly without waiting for Python.
- `content/altairApi.js`: completion entries for the editor.

Generated exercises compute their target at runtime by running their solution in the worker.

### Checker (`lib/checker.js`)

Both specs are normalised first:

- Drop `$schema`, `config`, `data`, `datasets`, `autosize` and `usermeta`.
- Turn a single-view spec into a one-element layer list. Merge any top-level `mark`, `encoding` and `transform` of a layered spec into each layer.
- Express marks as objects (`{type, ...props}`).
- Keep only the meaningful keys of each encoding channel: `field`, `type`, `aggregate`, `timeUnit`, `bin`, `value`, `sort`, `stack`, `title`, `scale`, `axis.format`, `legend.title`.

Checks are generated only for what the target specifies, matching layers by index:

1. Structure: same number of layers, or the same concat/facet layout.
2. Mark per layer: the type plus every property the target sets, as one check.
3. Each channel: field, type and aggregate as one check; each option the target sets (`sort`, `scale`, `axis.format`, `legend.title`, `title`, `stack`) as a separate check.
4. Transforms: compared by deep equality ignoring key order, one check per target transform.
5. Top-level `title`, `width` and `height` when the target sets them.

Each check has a short label ("y: sort by −x") and passes or fails. There is no percentage. An exercise is solved when every check passes.

### Generator (`lib/generator.js`)

Columns get roles from their metadata: categorical (N or O with 2 to 12 distinct values), quantitative, temporal. Templates declare which roles they need, and the generator only picks templates the dataset can satisfy.

- Beginner: bar of category against quantity (mean if categories repeat), scatter of two quantities coloured by a category, line of quantity over time.
- Intermediate: sorted horizontal bar with an aggregate and a named colour scheme, histogram with `bin`, filtered line chart coloured by category with a title.
- Advanced: bar with a layered mean rule, scatter with a regression line, faceted chart by category, top-N by window rank.

Each template produces a readable task text, two or three hints and solution code (dataset setup plus the chart). The target is the result of running that solution; if it errors, the generator tries another template. The random seed is part of the exercise id, so a generated exercise is reproducible.

### CSV upload (`lib/csv.js`)

A small parser that handles quoted fields, embedded commas, escaped quotes and CRLF. Types are inferred per column: numeric columns become Q, ISO dates become T and everything else N, with distinct counts and samples computed. The setup code passes the CSV text to `pd.read_csv(io.StringIO(...))`, written as a Python string literal. Uploads are capped at 5,000 rows and 1 MB to stay inside the `localStorage` quota, with a clear message when exceeded.

### Persistence (`lib/storage.js`)

One `localStorage` key, `altairlab:v1`, holding solved exercise ids, code per exercise and per sandbox dataset, custom datasets, generated exercises and the rail's collapsed state. Every read and write is wrapped in `try/catch`; if storage is unavailable the app works without saving. A "Reset progress" action sits in the rail footer behind a confirmation.

### Routing

Hash routes (`#/ex/10`, `#/sandbox/cars`) so GitHub Pages serves `index.html` for every route and links to an exercise can be shared.

## Error handling

- Pyodide or package load failure: status shows the failing step and a Retry button; targets still render because they're precomputed.
- Python exception: message and user line number in the Yours panel, chart cleared.
- No chart produced: specific hint about the last line.
- Run timeout: worker restarted, message shown.
- Vega render error (invalid spec or failed data fetch): the message appears in the chart panel.
- `localStorage` unavailable or full: the app keeps working and shows a one-line notice that progress isn't being saved.

## Testing

- Vitest unit tests for the checker (normalisation, layer merge, each check kind, real Altair output fixtures), the CSV parser, column role inference and the generator (every template on every built-in dataset produces valid solution code).
- `scripts/build-targets.mjs` doubles as an integration test: every curated solution must run under Pyodide.
- An extra Node script runs a sample of generated solutions under Pyodide.
- Manual check in a headless browser at desktop and phone widths before deploying.

- Initialise git, commit the original prototype first so the history shows the starting point, then the redesign.
- Create the public repo `feal-ca/altair-lab` with `gh`, enable Pages with GitHub Actions as the source.
- Fix the workflow: `npm ci` with a committed lockfile, Node 22, build, upload `dist`, deploy.
- Keep `base: './'` in Vite so assets resolve under `/altair-lab/`.
- Add a short README with what the app is, how to run it locally and how targets are rebuilt.
- After the first deploy, load the live URL and confirm an exercise runs end to end.

## Out of scope

- Accounts, server-side storage or sharing progress between devices.
- Lessons or a cheat sheet beyond the per-exercise concept notes.
- A dark theme.
- Translating the UI.
